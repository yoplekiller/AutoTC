확인해보니 8개 중 4개는 이미 사용자가 2026-08-09에 직접 커밋(`5880b1a1`)해놓은 상태였고, 이번엔 나머지 4개를 신규 추가.

### 2. TC 개수 하드코딩 제거 (커밋 `bcfb4ba`, push 완료)

"TC 개수 제한이 하드코딩돼 있으면 제거하고, 기획서에서 실제 검증 가능한 조건 기준으로만 생성하게 바꿔달라"는 요청 → 확인해보니 두 파일이 서로 다른 방식으로 문제였음.

- `generate_tc.py`: 프롬프트 텍스트로만 강제(이슈유형별 "N개 이상" 표 + "정확히 {count}개... 개수 미달 시 불합격"). 코드 레벨 강제는 없었음.
- `watch_sheet.py`: **코드 자체에 하드 플로어가 있었음** — `n = max(int(plan_dict.get(t, min_n)), min_n)`으로 AI가 산정한 값을 무조건 `minimums` 딕셔너리 값 이상으로 강제 클램핑. 프롬프트만 고쳐선 안 없어지는 진짜 코드 버그.

두 파일의 `analyze_spec_for_plan`에서 이슈유형별 최소/목표 개수 테이블 전부 삭제하고 "요구사항에서 실제로 검증 가능한 조건 수만큼만, 근거 부족하면 0, 개수 채우려고 중복·추정·임의 케이스 금지"로 재작성. `_call_tc_api`의 "정확히 N개... 미달 시 불합격"도 "N은 상한 아닌 참고치"로 변경.

부수 발견: `watch_sheet.py`의 `analyze_spec_for_plan`에 `response = None` 초기화가 없어서 rate limit 재시도 3번이 전부 실패하면 `UnboundLocalError`로 죽는 잠재 버그도 같이 수정.

### 3. QA Analysis / Human Confirmation 게이트 추가 (커밋 `4713d50`, push 완료)

기존엔 "기획서 링크 입력 → 즉시 TC 생성" 구조였는데, 중간에 정책 불명확성 검토 단계를 끼워넣는 요청. **사용자가 "구현 전 분석부터"를 명시적으로 요청**해서, 현재 구조(기획서 읽는 흐름/LLM 호출 위치/TC 프롬프트/시트 구조/실행 트리거/영향 범위 등)를 먼저 분석해서 답변으로 정리해 보여준 뒤, AskUserQuestion으로 3가지 설계 갈림길을 확인하고 나서 구현 시작.

**확정된 설계 (사용자가 전부 추천안 선택)**:
1. 2차 실행 트리거 = 새 인프라 없이 기존 시트 상태값("TC 생성") 변경만으로
2. QA Review 질문은 티켓별 탭이 아니라 공용 "QA Review" 탭 하나에 "기획서 키" 컬럼으로 구분
3. 적용 범위는 기획서 URL 직접 입력 경로만 (Jira 티켓 경로는 완전히 무변경)

**구현** (`src/watch_sheet.py` 한 파일만, 253줄 추가 — `generate_tc.py`의 TC 생성 프롬프트는 한 글자도 안 건드림):
- 새 흐름: 기획서 URL 입력 → Confluence fetch → **QA Analysis**(정책 불명확성 판단) → 불명확 없으면 기존처럼 바로 TC 생성 / 있으면 TC 생성 보류 + QA Review 탭에 질문 기록 + 상태 "QA 확인 필요 (N건)" → 사람이 답변 채운 뒤 상태를 "TC 생성"으로 직접 변경 → 다음 폴링에서 전부 답변됐는지 확인 후 원본 기획서 + 확정 답변을 합쳐 TC 생성
- 신규 함수 5개: `run_qa_analysis`(AI가 정책 임의 확정 안 하고 질문 형태로만 남기도록 프롬프트로 강제), `get_or_create_qa_review_sheet`, `append_qa_questions`(중복 방지), `read_qa_answers`(답변 완료 여부 판정 + 개별 행 상태 자동 갱신), `build_confirmed_spec`(원본+답변 결합, 기존 파이프라인에 그대로 흘려보냄)
- `scan_pending_rows`가 C열이 빈 값이거나 정확히 "TC 생성"인 행을 같이 스캔하도록 확장(1차/2차 구분)
